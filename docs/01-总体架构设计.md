# 01 · 总体架构设计

## 1. 架构目标

- **内核与界面彻底解耦**：内核工程不引用任何 UI 框架。
- **可测试**：核心逻辑可脱离网络/磁盘/进程运行（靠注入与桩）。
- **可组合**：服务以接口连接，实现可替换。
- **可移植**：平台差异集中在 `ACL.Platform.*`。
- **可演进**：对外契约稳定，内部实现可迭代。

## 2. 技术选型

| 维度 | 选择 | 理由 |
| --- | --- | --- |
| 运行时 | **.NET 10 (LTS)** | 长期支持、性能好、跨平台、现代 C# |
| 语言 | **C#**（最新稳定） | 表达力强、生态完善、工具链成熟 |
| UI | **Avalonia 12** | 跨平台 XAML + MVVM；Windows 可切 WPF 后端 |
| 配置/序列化 | **System.Text.Json**（默认）；Newtonsoft.Json 仅在需要兼容外部格式时 | 现代、高性能 |
| HTTP | `HttpClient` + `IHttpTransport` 抽象 | 可注入、可缓存、可重试 |
| 日志 | `Microsoft.Extensions.Logging` 抽象 + 自研 Sink | 结构化、可桥接 |
| DI | `Microsoft.Extensions.DependencyInjection`（仅组合根使用） | 标准、内核不感知容器 |
| 测试 | **xUnit** + 桩 HTTP/文件系统 | 与 .NET 生态一致 |
| 打包 | 单文件 / MSIX（Windows）、AppImage/tar（Linux）、.app（macOS） | 分平台 |

> 备选（若坚持 Windows-only 与最小迁移成本）：UI 用 **WPF**，其余不变。内核与 UI 解耦使该选择可后置。

## 3. 分层

```
┌───────────────────────────────────────────────────────────────────────────┐
│ Hosts 宿主：ACL.App (Avalonia/MVVM) · ACL.Cli · (future: ACL.Wpf)          │
└───────────────▲───────────────────────────────────────────▲──────────────┘
                │ 仅依赖 Abstractions / Contracts             │
┌───────────────┴───────────────────────────────────────────┴──────────────┐
│ Application 应用层：用例编排（启动/安装/导入/检索/导出）                      │
└───────────────▲──────────────────────────────────────────────────────────┘
┌───────────────┴──────────────────────────────────────────────────────────┐
│ Services 领域服务：Tasks/Download/Version/Java/Auth/Launch/Resources/…     │
└───────────────▲──────────────────────────────────────────────────────────┘
┌───────────────┴──────────────────────────────────────────────────────────┐
│ Domain 领域模型：纯数据 + 纯算法（版本/实例/组件/清单/Java 规格/计划）          │
└───────────────▲──────────────────────────────────────────────────────────┘
┌───────────────┴──────────────────────────────────────────────────────────┐
│ Abstractions 抽象：接口 / DTO / 枚举 / 错误码 / 事件                         │
│ Infrastructure 实现：Http / 文件系统 / 进程 / 时钟 / 配置 / 日志              │
│ Platform 适配：Windows / Linux / macOS 专属能力                             │
└──────────────────────────────────────────────────────────────────────────┘
```

**依赖方向只能向下**：`Hosts → Application → Services → Domain → Abstractions`；`Infrastructure` / `Platform` 只实现 `Abstractions`，由组合根注入。

## 4. 工程划分

```
src/
├─ ACL.Core.Abstractions/   接口、DTO、枚举、错误码、事件（无实现，无外部依赖）
├─ ACL.Core.Domain/         领域模型与纯算法（版本比较、序数编码、组件等价判定）
├─ ACL.Core.Tasks/          任务流水线引擎（阶段图、进度树、取消、重试）
├─ ACL.Core.Download/       下载调度、多源、分片、断点、校验、镜像策略
├─ ACL.Core.Version/        清单/元数据/JSON 解析、安装与补全
├─ ACL.Core.Java/           Java 探测/搜索/选择/安装
├─ ACL.Core.Auth/           微软/离线/第三方认证与令牌管理
├─ ACL.Core.Launch/         参数、natives、进程启动与监控
├─ ACL.Core.Resources/      CurseForge / Modrinth / 本地资源
├─ ACL.Core.Modpack/        整合包格式识别与安装
├─ ACL.Core.Diagnostics/    崩溃归因、日志导出
├─ ACL.Application/         用例编排（依赖 Services）
├─ ACL.Infrastructure/      Http/文件/进程/时钟/配置/日志默认实现
├─ ACL.Platform.Windows/    注册表、GPU 偏好、内存、窗口句柄
├─ ACL.Platform.Unix/       Linux/macOS 实现
├─ ACL.App/                 Avalonia 界面（MVVM）
└─ ACL.Cli/                 命令行宿主
tests/
├─ ACL.Core.*.Tests/        各内核层单测
└─ ACL.Integration.Tests/   桩服务/端到端集成测试
```

**规则**：
- 内核工程（`ACL.Core.*`、`ACL.Application`）**禁止**引用 Avalonia/WPF/控制台。
- `ACL.App`/`ACL.Cli` **禁止**被内核引用。
- 一个工程一个职责；新增工程需在本文档登记。

## 5. 组合根（Composition Root）

- 仅由宿主（`ACL.App` / `ACL.Cli`）负责注册实现：`ServiceCollection` 或手写工厂。
- 内核组件通过构造函数注入依赖（`IHttpTransport`、`IFileSystem`、`ISystemClock`、`IAppLogger` …）。
- **内核不解析容器**（不使用 service locator）。

示例（伪码）：

```csharp
var services = new ServiceCollection();
services.AddSingleton<ISystemClock, SystemClock>();
services.AddSingleton<IFileSystem, PhysicalFileSystem>();
services.AddSingleton<IHttpTransport, HttpTransport>();
services.AddSingleton<IAppLogger, FileLogger>();
services.AddSingleton<IMirrorPolicy, MirrorPolicy>();
services.AddSingleton<IDownloadService, DownloadService>();
services.AddSingleton<IVersionCatalog, VersionCatalog>();
services.AddSingleton<IAuthService, AuthService>();
services.AddSingleton<ILaunchService, LaunchService>();
services.AddSingleton<ISecretProvider, EnvironmentSecretProvider>();
```

## 6. 跨平台策略

| 关注点 | 处理 |
| --- | --- |
| 路径 | 统一 `Path` + 规范化；Windows 大小写不敏感由比较器处理 |
| 进程/退出码 | `IProcessLauncher` 抽象；平台差异在 `Platform` |
| 系统能力 | GPU 偏好/内存优化/注册表仅 Windows，缺失即 no-op（可选能力） |
| 窗口句柄/DPI | 仅 UI 层；内核不感知 |
| 编码 | 文本 UTF-8；外部日志用探测回退 |
| 打包 | 分平台产出 |

## 7. 分层使用的统一模式

1. **用例编排在 Application**：如 `LaunchOrchestrator` 组合 Version/Java/Auth/Launch。
2. **服务只做单一职责**，通过接口互相引用（见 [03](03-服务设计规范.md)）。
3. **进度与事件对外**：服务不弹窗、不写界面，只发 `IProgressSink` 事件与结果。
4. **宿主订阅并渲染**：UI 把进度/状态映射为界面；CLI 映射为文本。
