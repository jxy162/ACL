# 11 · 决策记录（ADR）与变更日志

> 重大架构/技术决策记录于此，便于回溯"为什么这样做"。
> 每个决策：编号、状态、背景、决定、后果。

## ADR 模板

```
### ADR-XXXX 标题
- 状态：提议 / 已接受 / 已废弃 / 被取代
- 日期：YYYY-MM-DD
- 背景：要解决什么问题、有哪些约束
- 决定：选择了什么
- 后果：好处 / 代价 / 后续影响
```

## ADR 列表

### ADR-0001 采用 .NET 10 (LTS) 与 C#
- 状态：已接受
- 日期：2026-10-22
- 背景：需要现代、跨平台、可测试的运行时；既有实现基于 .NET Framework 4.8 + VB，迁移成本与生态限制较大。
- 决定：内核与界面均采用 **C# + .NET 10 (LTS)**。
- 后果：获得跨平台与现代化工具链；需注意平台工程的目标框架（`net10.0-windows` 等）。

### ADR-0002 界面采用 Avalonia（跨平台），内核零 UI 依赖
- 状态：已接受
- 日期：2026-10-22
- 背景：希望 UI 可替换且内核可跨平台复用；Windows-only 的 WPF 不满足跨平台目标。
- 决定：UI 使用 **Avalonia 12 + MVVM**；内核工程**禁止引用任何 UI 框架**。
- 后果：跨平台前景好；需为平台专属能力（GPU/注册表/窗口）做 `Platform` 抽象；备选可换 WPF 后端。

### ADR-0003 净室自研（Clean-room）
- 状态：已接受
- 日期：2026-10-22
- 背景：需自研一个不派生自任何既有启动器的实现，规避许可与代码来源风险。
- 决定：只依据**公开规范**与**外部行为**独立实现；**不复制、不沿用**他方源码与命名。
- 后果：实现成本更高；但许可自主、结构可控。研究记录见 [10](10-参考实现研究-PCL与ACL架构剖析.md)。

### ADR-0004 内核严格分层与依赖方向
- 状态：已接受
- 日期：2026-10-22
- 背景：避免重蹈"逻辑与 UI 纠缠、全局状态泛滥"的覆辙。
- 决定：`Hosts → Application → Services → Domain → Abstractions` 单向依赖；`Infrastructure/Platform` 仅实现抽象；禁止跨层与反向引用。
- 后果：清晰可测；需维护工程边界与组合根。

### ADR-0005 序列化默认 System.Text.Json
- 状态：已接受
- 日期：2026-10-22
- 背景：需要高性能、现代的序列化；但需读写多种外部格式（Mojang/CF/Modrinth）。
- 决定：默认 `System.Text.Json`；仅在外部格式确有需要时使用 Newtonsoft.Json。
- 后果：减少依赖；个别格式需自定义转换器。

### ADR-0006 多源镜像 + 取先返回
- 状态：已接受
- 日期：2026-10-22
- 背景：官方源在部分地区不稳定；镜像可用性不一。
- 决定：请求采用"官方 + 镜像"有序候选，**并发送取先返回者**，失败自动切源；镜像可插拔。
- 后果：提升可用性；需处理并发请求与结果一致性。

### ADR-0007 错误模型：Result + ErrorCode，文案在宿主
- 状态：已接受
- 日期：2026-10-22
- 背景：内核不应内联用户文案（国际化/复用）。
- 决定：预期失败返回 `Result<T>(ErrorCode, Detail)`；宿主把 `ErrorCode` 映射为本地化文案。
- 后果：内核语言无关；需维护错误码表。

---

### ADR-0008 产品名称定为 ACL
- 状态：已接受
- 日期：2026-10-22
- 背景：需要确定正式产品名与品牌标识，以统一程序集名、窗口标题、界面文案与发布物。
- 决定：产品正式名称定为 **ACL**（不再使用"名称待定/工程代号"表述）；命名空间与工程名保持 `ACL.*`。
- 后果：命名稳定；关于页、发布说明、商标声明均以 ACL 呈现，并继续避免与任何官方/第三方名称混淆。
