# 11 · 决策记录（ADR）与变更日志

> 重大架构/技术决策记录于此，便于回溯"为什么这样做"。
> 每个决策：编号、状态、背景、决定、后果。


## ADR 列表

### ADR-0001 采用 .NET 10 (LTS) 与 C#
- 状态：已接受
- 日期：2026-10-22
- 背景：需要现代、跨平台、可测试的运行时；既有实现基于 .NET Framework 4.8 + VB，迁移成本与生态限制较大。
- 决定：内核与界面均采用 **C# + .NET 10 (LTS)**。
- 后果：获得跨平台与现代化工具链；需注意平台工程的目标框架（`net10.0-windows` 等）。

### ADR-0002 界面采用 Avalonia（跨平台），内核零 UI 依赖
- 状态：已接受
- 日期：2026-10-22
- 背景：希望 UI 可替换且内核可跨平台复用；Windows-only 的 WPF 不满足跨平台目标。
- 决定：UI 使用 **Avalonia 12 + MVVM**；内核工程**禁止引用任何 UI 框架**。
- 后果：跨平台前景好；需为平台专属能力（GPU/注册表/窗口）做 `Platform` 抽象；备选可换 WPF 后端。

### ADR-0003 净室自研（Clean-room）
- 状态：已接受
- 日期：2026-10-22
- 背景：需自研一个不派生自任何既有启动器的实现，规避许可与代码来源风险。
- 决定：只依据**公开规范**与**外部行为**独立实现；**不复制、不沿用**他方源码与命名。
- 后果：实现成本更高；但许可自主、结构可控。研究记录见 [10](10-参考实现研究-PCL与ACL架构剖析.md)。

### ADR-0004 内核严格分层与依赖方向
- 状态：已接受
- 日期：2026-10-22
- 背景：避免重蹈"逻辑与 UI 纠缠、全局状态泛滥"的覆辙。
- 决定：`Hosts → Application → Services → Domain → Abstractions` 单向依赖；`Infrastructure/Platform` 仅实现抽象；禁止跨层与反向引用。
- 后果：清晰可测；需维护工程边界与组合根。

### ADR-0005 序列化默认 System.Text.Json
- 状态：已接受
- 日期：2026-10-22
- 背景：需要高性能、现代的序列化；但需读写多种外部格式（Mojang/CF/Modrinth）。
- 决定：默认 `System.Text.Json`；仅在外部格式确有需要时使用 Newtonsoft.Json。
- 后果：减少依赖；个别格式需自定义转换器。

### ADR-0006 多源镜像 + 取先返回
- 状态：已接受
- 日期：2026-10-22
- 背景：官方源在部分地区不稳定；镜像可用性不一。
- 决定：请求采用"官方 + 镜像"有序候选，**并发送取先返回者**，失败自动切源；镜像可插拔。
- 后果：提升可用性；需处理并发请求与结果一致性。

### ADR-0007 错误模型：Result + ErrorCode，文案在宿主
- 状态：已接受
- 日期：2026-10-22
- 背景：内核不应内联用户文案（国际化/复用）。
- 决定：预期失败返回 `Result<T>(ErrorCode, Detail)`；宿主把 `ErrorCode` 映射为本地化文案。
- 后果：内核语言无关；需维护错误码表。

### ADR-0008 产品名称定为 ACL
- 状态：已接受
- 日期：2026-10-22
- 背景：需要确定正式产品名与品牌标识，以统一程序集名、窗口标题、界面文案与发布物。
- 决定：产品正式名称定为 **ACL**（不再使用"名称待定/工程代号"表述）；命名空间与工程名保持 `ACL.*`。
- 后果：命名稳定；关于页、发布说明、商标声明均以 ACL 呈现，并继续避免与任何官方/第三方名称混淆。


### ADR-0009 接口归位：跨切面抽象在 Abstractions，领域型服务接口随服务工程
- 状态：已接受
- 日期：2026-10-22
- 背景：文档规定 `Abstractions` 承载"所有 I*"，但部分服务接口签名依赖 `Domain` 模型（如 `IDownloadService` 使用 `DownloadItem`）。若这些接口置于 `Abstractions`，将与其依赖方向（`Domain → Abstractions`）形成循环引用。
- 决定：
  1. **仅依赖 BCL / 基础类型**（`Uri`、`Stream`、原始类型）的跨切面抽象置于 `ACL.Core.Abstractions`（如 `IHttpTransport`、`IFileSystem`、`ISystemClock`、`IProgressSink`、`IAppLogger`、`IMirrorPolicy`、`IMirrorProvider`）。
  2. **签名依赖领域模型**的服务接口与其默认实现置于对应服务工程（如 `IDownloadService` 在 `ACL.Core.Download`）。
- 后果：消除循环依赖；服务接口与实现同工程，调用方按需引用服务工程。同步更新 [02](02-内核架构与模块划分.md) 模块表说明。

### ADR-0010 下载源策略分层：文件有序回退、元数据并发取先
- 状态：已接受
- 日期：2026-10-22
- 背景：ADR-0006 要求"并发送取先返回者"。对元数据（小文件）该策略降低延迟；但体积较大的库 / 资源 / 安装包若并发整文件下载，会浪费带宽且不利于断点续传。
- 决定：源策略按对象规模分层——
  1. **文件下载**（库 / 资源 / Java / 安装包）采用**有序候选 + 失败切源**，配合 `.part` 断点续传与 Range 回退（`DownloadService` 已实现）。
  2. **元数据请求**（版本清单 / 版本 JSON / 加载器元数据）采用**并发取先返回者**（在 M3 `VersionService` 落地）。
  两种方式的候选序仍统一由 `IMirrorPolicy` 提供。
- 后果：兼顾低延迟与带宽效率；需分别实现两种执行策略。ADR-0006 的"候选序"概念不变。

### ADR-0011 界面设计语言：参考 APCL 定稿 UI，独立重写（不接入、不逐像素复刻）
- 状态：已接受
- 日期：2026-10-22
- 背景：希望 ACL 的界面延续既有 APCL 界面的体验方向（Material 3 Expressive + Xbox 风格全屏仪表盘），同时必须保持"完全自研"（ADR-0003）、自有命名（ADR-0008）与 Avalonia 技术栈（ADR-0002）。
- 决定：
  1. 仅把 APCL 定稿界面作为**设计语言参考**（配色方向、圆角 / 卡片 / 导航形态、全屏仪表盘结构、动效取向），见 [12-界面设计语言](12-界面设计语言.md)。
  2. **不接入**其代码 / XAML / 资源；不复制模板与命名；**不逐像素复刻**——须可辨识为不同实现。
  3. 组件、设计令牌、LOGO / 壁纸 / 图标全部在 ACL 内以 Avalonia 自行实现或自行生成。
- 后果：体验方向一致、实现完全自研；M8 需投入自绘与资源生成成本；验收以"并排可辨识为不同实现"为准。

### ADR-0012 便携式布局：数据与 .minecraft 同启动器目录
- 状态：已接受
- 日期：2026-10-22
- 背景：希望启动器可整体拷贝使用，且文件位置直观、便于查找。
- 决定：默认把**启动器数据目录**设为启动器可执行文件所在目录，**游戏目录**设为同目录下的 `.minecraft/`；可用环境变量 `ACL_GAME_DIR` 覆盖。CLI 与界面一致。
- 后果：便携、路径直观；不再默认写入用户应用数据区。若需与既有启动器共用游戏目录，显式设置 `ACL_GAME_DIR` 即可。

### ADR-0013 密钥来源：ACL 自有（便携文件 / ACL_* 环境变量），不与 PCL 互通
- 状态：已接受
- 日期：2026-10-22
- 背景：ACL 使用**本项目作者本人申请**的密钥（Microsoft 应用 Client ID、CurseForge API Key），既不硬编码进源码，也不依赖任何其他启动器的密钥机制。
- 决定：`ISecretProvider` 采用组合顺序——(1) 启动器目录下的 `ACL.secrets.json`（便携、已 gitignore）；(2) 环境变量 `ACL_MS_CLIENT_ID` / `ACL_CURSEFORGE_API_KEY`。**不与 PCL 或其他启动器共享/互通密钥**；仓库仅提供占位示例 `ACL.secrets.example.json`。
- 后果：密钥与产品自有命名一致、可便携分发；若把 `ACL.secrets.json` 随包分发则存在泄露风险，发布时应剔除或改用环境变量注入。
